# #123 P2.1a — Codex re-review

Date: 2026-07-27  
Basis: absorption commit `568313c`  
Verdict: **REVISE**

## Executive judgment

F1 and F3 are substantively resolved. The thin prompt now has a coherent eligibility-then-cut
procedure, and the fat prompt now has a usable relevance/ranking hierarchy. F4 is resolved through
one checked parser. Raising `SYSTEM_TEMPLATE_BUDGET_BYTES` to 4,096 B is the right owner call.

One load-bearing absorption gap remains before P2.1f: H04 sanitizes `slug` and `title` but
interpolates `page_type` unchanged. `PageType` is only a static `Literal`; there is no runtime
validation in `SpaceEntity`, and Kuzu stores `page_type` as an unconstrained string. A runtime value
of `"concept\nQUERY:"` still forges an unindented `QUERY:` line. The 12 H04 tests do not cover that
field, and their line-break oracle omits three separators.

Fix that boundary and correct the byte-preservation claim before freezing. The remaining prose item
below is small and can be absorbed without expanding the prompt.

## Findings

### R1 — HIGH — H04's “exactly one line for any input” property is still false

`kdb_search/projection.py:108-112` applies `_single_line` to `entity.slug` and `entity.title`, but
not to `entity.page_type`:

```python
SpaceEntity(slug="s", title="T", page_type="concept\nQUERY:")
```

still renders as two lines, with the second line exactly `QUERY:`.

The annotation at `kdb_search/types.py:62-69` does not enforce the `PageType` `Literal` at runtime;
`SpaceEntity` has no validation. The durable graph does not enforce it either:
`kdb_graph/schema.py:62-66` declares `page_type STRING`, and
`kdb_graph/intake.py:321-327` writes the producer value directly. No search-space materializer
currently exists to establish a checked runtime boundary.

Required before pinning: apply `_single_line` to `page_type` as well, and add the same forged-header
regression for all three interpolated fields. Separately, the future graph-to-search materializer
should validate semantic membership in the canonical page-type vocabulary; defensive prompt
serialization must not rely on type hints for P10 containment.

The narrower hand-authored-ingest trust path corrects my first review's rationale, but not the
remedy. It strengthens the case for two layers:

1. projection-level containment for every interpolated field, protecting this prompt; and
2. validation at the durable graph ingestion/materialization boundary, protecting MCP, CLI,
   viewer, and future consumers from malformed titles/page types rather than making each consumer
   rediscover the rule.

The second item is ingestion hygiene outside P2.1a; it should not replace the local containment fix.

### R2 — MEDIUM — The H04 tests do not yet pin the stated universal property

`kdb_search/tests/test_projection.py:91-108` hardcodes inputs for `\n`, `\r`, `\r\n`, `\v`, `\f`,
`\x1c`, `\x85`, and U+2028. The production set at
`kdb_search/projection.py:58-62` also contains `\x1d`, `\x1e`, and U+2029. Those three are not used
as inputs. The assertion at `test_projection.py:106` derives its expected forbidden set from the
production `_LINE_BREAKS`, so removing an omitted character from both production behavior and that
set would stay synchronized and pass.

The tests also cover forged breaks in title and slug, but not `page_type`, which is why R1 passes
the suite.

Recommendation: define a hardcoded, independent test oracle containing all ten single-character
`str.splitlines()` boundaries plus the CRLF pair; parameterize each interpolated field over it; and
assert `len(render_thin_line(...).splitlines()) == 1`. Do not derive the oracle from
`projection._LINE_BREAKS`.

### R3 — MEDIUM — “Byte-count preserving” is false; the useful property is UTF-8 non-expansion

`kdb_search/projection.py:85-89` says replacing one character with one space is byte-count
preserving. That is true for ASCII breaks but false for multibyte separators: `"A\u2028B"` is
5 UTF-8 bytes, while `_single_line("A\u2028B")` is 3.

`kdb_search/tests/test_projection.py:138-143` does not prove input-to-output byte preservation. It
compares the already-sanitized malformed rendering with a clean rendering, which proves equivalent
output shape/length. The behavior is still safe for the budget: every supported break encodes to at
least one byte, and the replacement is one ASCII byte, so sanitization is **UTF-8 non-expanding**.
On the frozen fixture it is byte-neutral because no value changes.

Recommendation: retain collapse-to-space, but change the implementation/plan/test claims from
“byte-count preserving” to “character-count preserving and UTF-8 non-expanding.” Test
`len(_single_line(value).encode()) <= len(value.encode())`, including U+2028/U+2029. The mutation
that emits a visible two-character `\\n` is correctly rejected because it expands ASCII line breaks;
it does not establish equality for multibyte breaks.

This is a claim/test correction, not a request to change `_single_line`'s output behavior.

### R4 — LOW — One fat-ranking phrase weakens the otherwise-correct positive-support rule

`kdb_search/prompts/selector_fat_v1.txt:29-35` orders centrally-about entities, then substantial
supporting coverage, “then the rest.” “The rest” is ambiguous after
`:23-27` says positive support only and `:50-51` calls weak padding a defect. It can be read as an
instruction to include the remaining candidates.

The absorption record also says both templates prohibit stopping once the list could be filled
(`docs/superpowers/plans/2026-07-27-task123-p2-implementation-plan.md:259-268`), but only the thin
template states that prohibition explicitly (`selector_thin_v1.txt:33-35`). The fat prompt prohibits
using EVIDENCE order, which is useful, but does not explicitly require ranking the full supported
set before cutting to 50.

Recommended compact replacement:

> Entities the QUERY is centrally about come first, followed by entities giving substantial
> supporting coverage. Rank the full supported set before cutting to the limit: never stop when the
> list fills or treat EVIDENCE order as a relevance signal.

This removes “the rest,” closes the record/template discrepancy, and should be byte-neutral or
smaller after folding in the existing final sentence.

## Answers to the six questions

1. **F1's two steps resolve the contradiction.** Eligibility and cutting are distinct and
   executable. “Precision among the retained is [stage 2's] job” is correctly scoped to the
   retained set; the binding-cap paragraph explicitly says a weak retention is not free. “Read
   every identity before deciding anything” would be slightly more literal as “before finalizing
   the shortlist,” but it does not create a substantive conflict.
2. **The fat block is not over-instructed.** `WHAT TO SELECT` defines membership and
   `HOW TO ORDER` defines order; that separation helps rather than dilutes. Remove “then the rest”
   per R4. The positive-support wording is repeated, but the repetition is load-bearing enough to
   keep.
3. **Raise the reserve to 4,096 B.** The stronger reason is architectural capacity, not that a
   frozen v1 prompt needs another sentence. A golden pin should force version/review discipline for
   content changes; the 4,096 B reserve independently lets future reviewed prompt versions evolve
   without a blueprint amendment for ordinary prose changes. It costs only 1,024 B against ~36.8k
   of declared-guarantee slack and leaves `284,192 < 320,000`. Matching the query reserve is a useful
   secondary simplification. Record blueprint v0.15 before changing the constant.
4. **H04 choices:** collapse to space is preferable to a visible `\\n` escape because a title line
   break is structural/malformed data and the visible two-character form expands ASCII inputs.
   Cover the full `str.splitlines()` set because the invariant is line-based. Not counting the
   locally removed anomaly is reasonable: no P2 decision consumes the count. Correct the property
   to UTF-8 non-expansion per R3, and apply it to `page_type` per R1. Broader durable-ingest
   validation should be handled at that boundary, not by adding search telemetry with no consumer.
5. **F4 is now one checked path.** `_version_of()` is declared before both constants and is reused by
   `load_template` (`kdb_search/prompts.py:77-101,142-149`). Its malformed-name tests exercise the
   parser directly. The H04 tests pin several important examples and behavioral dimensions, but not
   the full stated property; R1/R2 identify the missing field and oracle values.
6. **Absorption breakage/gaps:** R1 is the behavior the passing suite misses; R3 is the false
   arithmetic claim its test does not establish; R4 is the prose/absorption-record discrepancy. No
   other regression was found.
