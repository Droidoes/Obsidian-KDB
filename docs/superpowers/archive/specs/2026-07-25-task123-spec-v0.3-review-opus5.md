## 1. Confirmations requested

### 1.1 A1 supersession — confirmed

I confirm the extended reading of §2.3/§3.4: per-entry salvage for all entry classes, controller-computed
accounting, retry-once, honest empty, no deterministic substitution anywhere in the contract, all three T2Modes
retired, the resolver surviving only as annotation instrumentation. My A1 is superseded and should be marked so
in the vision.

**But the stated rationale does not support the ruling, and the record should say why the ruling is still right.**
§3.4 argues the fallback would be "a silent reversion to pre-#123 behavior." Pre-#123 behavior is what
`STRUCTURED` delivers — 0–2 T2 hits per source on the 2026-07-25 cold runs. So:

- **with** a fallback, a selector failure lands at roughly today's behavior (a few exact hits);
- **without** one, a selector failure lands *strictly below* today's behavior (zero hits).

"It only reverts to status quo" is therefore an argument for the fallback being *low-value*, not for it being
*harmful*. R1 makes the failure mode worse than status quo, and that should be on the record as a deliberate
trade rather than as a neutral cleanup.

**The trade is nonetheless correct, for two reasons §3.4 doesn't give:** (a) a silent partial-quality path that
resembles success corrupts the one signal that tells us whether #123 works — honest empty plus a
selector-failure-rate hard gate is the measurable choice; (b) keeping the fallback keeps `STRUCTURED` as a live
production path, i.e. two T2 architectures indefinitely. Both outweigh recovering 0–2 hits on a gated-rare path.

### 1.2 Three minors — confirmed landed

Selector-failure-rate hard gate (§8.4), `max_results = 50` + `cap_exhausted_possible` (§3.2/§2.3), and
exact_matchable delta computed against the §1.1 annotation instrument (§8.3) are all resolved as intended.

## 2. Items

### 2.1 REQUIRED — R1's cost is unmeasurable as specified, which makes it a one-way door

`identity_match_annotations` hangs off `Hit` (§1.1), and on `status: selector_failure` there are no hits. So on
exactly the path R1 creates — retry-exhausted, empty T2 — **we record nothing about what the deterministic
resolver would have returned.** The instrument that would let us price R1's trade is absent precisely where the
trade is made.

**Fix (one telemetry field):** on `selector_failure`, record the deterministic resolver's would-be result set as
telemetry — `foregone_deterministic_hits: [slug]` — explicitly **not** as hits, never surfaced to pass-2. It is
already computed on every request (§1.1), so this is a persistence change, not new machinery.

Why it matters: with it, "should the fallback come back?" becomes a data question answerable from production
telemetry after the first cohort, and R1 stays reversible on evidence. Without it, R1 is justified by an argument
that runs backwards (§1.1 above) and leaves no way to check itself. This is the one item I'd want in v0.4 rather
than deferred to blueprint.

### 2.2 R4's justification overclaims — the stage-1 gate is vacuous at current scale

The R4 row (§7.2, §11) justifies always-two-stage partly as: "the stage-1 recall gate is exercised (and
measured) on 100% of production traffic from day one." The same row then admits the gate "cannot bind until a
domain exceeds 150 entities." Both are in the spec; only the second is true in the sense that matters.

With the largest domain at 51 entities and M = 150, stage-1 retention is **retain-all**, so recall@150 is 1.0 by
construction on every domain-scoped probe and mildly binding (150 of 163) only on whole-graph probes. The code
path is exercised; the *gate* measures nothing.

This does not undermine R4 — uniformity, no behavioral discontinuity, and one code path are sufficient
justification on their own. Drop the "measured from day one" clause, or restate it as "the code path is exercised
from day one; the gate becomes informative only above M." (Same species as v0.1's "no recall cap in stage 1"
wording, which was corrected the same way.)

### 2.3 REQUIRED — the SD-4 gate cannot be evaluated on the ratified substrate

SD-4 predeclares stage-1 recall@150 as a hard gate "run **before** vault ingestion" (§7.2, §8.4), and R3 fixes
the truth set to the 163-entity fixture (§8.1). Those two are incompatible: on that fixture M = 150 is
non-binding, so the gate returns 1.0 regardless of selector quality. The first scale at which recall@150 could
bind is vault scale — which is the thing the gate is supposed to authorize.

As specified, the gate is unfalsifiable before the event it gates.

**Fix — give the gate a measurable experimental form on the available substrate.** Measure stage-1 recall at a
**reduced M** where the fixture makes it binding (e.g. M = 10 and M = 20 over the 51-entity value-investing
domain, and M = 20/40 over the 163-entity whole graph), and predeclare the threshold on *that* curve; M = 150
remains the production constant. What we actually need to know is whether thin-title LLM selection retains
relevant identities when it must discard — a property measurable at any ratio, and the honest test of the
vision-Q3 skepticism the two-stage design rests on. State the reduced-M protocol in §8.3 metric 2 so the gate
has a definition before labeling begins.

### 2.4 Unattributed hits confound semantic abstention accuracy

§2.3 coerces unknown `matched_expression` values by removing them, leaving "an unattributed hit stands," and
§1.1 permits `matched_expressions: []`. Controller accounting then marks an expression *unresolved* unless a
validated hit attributes it. So a genuinely relevant entity can be present in `hits` while its expression is
reported unresolved — and §8.3 metric 6 scores that as an abstention judgment.

This is the mirror of the cap artifact you already fixed. Same treatment: count unattributed hits and exclude
affected expressions from abstention scoring, alongside `cap_exhausted_possible`.

### 2.5 Observation — at vault scale thin becomes the cost driver, which inverts the concordance question

From §7.1's own numbers: at vault, per source in the largest domain, thin ≈ 40k–70k tokens vs fat ≈ 14.5k. **The
thin stage costs 3–5× the fat stage** — the reverse of today (thin ~1k, fat ~5k).

Consequence for §8.3's concordance series, framed as "does fat earn its cost": at vault the operative question
becomes *does thin earn its cost*, and the natural simplification is not thin-only but **sharded fat** (option 3,
currently the stage-1-gate-failure contingency). Worth stating in §8.3/§10 so the concordance metric isn't read
at vault scale as answering a question it was designed for at 163 entities. No change to R4 implied.

### 2.6 Two minor clarifications

1. **§7.2's "stage 2 always fits" is a derived claim with unstated premises.** It holds for (M = 150, 250w bound,
   ≥64k window): 150 × ~366 tokens (250w + the +10% sentence extension, safety-bound) ≈ 55k. State the premises
   and assert the bound in a test, since §9's budget tests cover stage 1 only.
2. **Retry granularity in the artifact.** `stages: [...]` is "one entry per executed stage" while `attempt: int`
   lives *inside* a stage entry. With a retried call, is that two stage entries or one? Failure auditing needs
   the former — each attempt's rendered messages and raw response archived separately (that is the whole point of
   codex F4). One clause in §5.1.

## 4. Additions that improve on what the panel asked for

- **codex F4's rendered-message + raw-response archival** — byte fidelity that survives serializer drift, and it
  makes the malformed/timeout cases auditable rather than merely counted. Strictly better than hashing.
- **The §5.1 payload/envelope split** — one type shape for consumers that have no `run_id`/`source_id`. This is
  the cleanest expression yet of the consumer-neutral core the vision asserted.
- **`valid_entry_yield` + per-class attempted violations as per-model leaderboard series** — turns R1's salvage
  posture into selector-quality evidence instead of hidden leniency. It is what makes salvage safe.
- **§2.1's manifest-order stage-2 evidence** (fat unanchored to thin's ranking) — a subtle anti-anchoring control
  neither reviewer asked for, and it is what makes the concordance series interpretable.

Nothing above blocks ratification under R3's narrower gate. §2.1 and §2.3 are the two items I'd fold into v0.4
before the D7 program starts, because both change what gets built and measured rather than how it is described.
