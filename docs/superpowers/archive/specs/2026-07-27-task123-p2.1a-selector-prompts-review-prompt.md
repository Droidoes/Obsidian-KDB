## Binding context — please do not re-litigate

These are owner rulings or already-ratified, and a finding that reopens one is not actionable at
this phase. Findings about their **mechanics** are very much wanted.

- **D10** — invariant-first ordering: `EVIDENCE` before `QUERY` in the USER message, **both
  stages**, asserted by test. The query is last so it sits adjacent to the generation point.
  Ratified as an official fix, explicitly *not* as an experiment arm.
- **D11** — expressions addressed by **letter key-label** (`A`, `B`, …), never index. Lowercase is
  case-folded; an out-of-vocabulary label is coerce-dropped and counted; an integer is not a label.
- **D8** — the fat wire is compact: `{"selections":[{"slug","matched"}],"unresolved":[…]}`. The
  per-hit free-prose `evidence` field is **dropped** and stays dropped.
- **`json_mode=True`** on the selector call (Joseph, 2026-07-27) — loose JSON-object mode, syntax
  only. The prose still carries the schema and an example; openai-compat additionally 400s unless
  the literal word "JSON" appears in the messages, which is asserted.
- **Constants:** `M = 100` (thin retention + fat hydration cap), `MAX_RESULTS = 50`,
  `MAX_EXPRESSIONS = 10`, `SYSTEM_TEMPLATE_BUDGET_BYTES = 3,072`.
- **One file per stage**, both halves inside it. `PromptRef` carries one `version`, one `sha256`,
  one `repo_path`; a two-file stage would need two refs, and the owner's prose review is over one
  rendered prompt per stage.
- **R4 / D3** — always two-stage, every source, every run. Below `M` the controller feeds stage 2
  **every** eligible identity regardless of the thin response (retain-all), so thin's product is
  non-load-bearing *today*; the largest domain projects to **~490 against M=100** after the queued
  1,586-note vault ingestion, which is when it becomes binding.

## Deliberately deferred, not missed

- **P2.1f golden byte pins** — split from P2.1a on purpose. The pin is the only P2 artifact coupled
  to prose *content*; P2.2–P2.6 couple only to structure. So orchestration proceeds on these drafts
  while the prose is out for review, and the pins land after the review and before D5 calibration.
- **The built-wheel smoke test is not a wheel.** `.venv` has no `setuptools`, `build` or `wheel`, so
  building one needs a network install. Covered in two halves instead: the packaging **declaration**
  is parsed out of `pyproject.toml` and its globs expanded (so a new prompt file added without a
  packaging update fails), and resolution is proved by a subprocess with `cwd` outside the repo and
  `PATH` emptied (which also pins `git_commit == "unknown"`, the installed-wheel case). Tell us if
  this substitution leaves a real gap.
- **H04, filed not fixed** — `projection._scalar_lines` splits a field value on `"\n"` and indents
  every continuation line, so an injected `"""` or section header renders as content. **`render_thin_line`
  does neither**: it interpolates `title` into one f-string, so a title containing `\nQUERY:`
  injects an **unindented** line into the evidence block. Filed as a P2.7 H-class fixture rather
  than fixed, because the thin line is golden-pinned P1 code. Bounded: titles come from the graph,
  never from the wire, and `response.py` never reads identity from a response. **See question 6.**

## Measured figures — check the arithmetic

The `SYSTEM_TEMPLATE_BUDGET_BYTES` obligation was P2.1a's, and the constant holds, so no blueprint
bump. Overhead = rendered system block + user wrapper with both content slots empty, in **bytes**,
measured with the widest cap value the contract allows:

| | system | wrapper | total | headroom vs 3,072 |
| --- | --- | --- | --- | --- |
| fat | 2,321 B | 60 B | **2,381 B** | **691 B** |
| thin | 2,085 B | 61 B | **2,146 B** | 926 B |

Fat is the normative one — `budget.fat_worst_case_request_bytes()` is the constant's only consumer,
and it is fat's static guarantee that rests on it. Thin is estimate-guarded with a typed
`budget_estimation_miss`.

Stage-2 bound, now measured rather than part-declared: `100 × 2,500 + 4,096 + 2,381 = 256,477 B`
≤ ~257 kB; under `tokens_lte_bytes` that bounds tokens, `+ 26,000` reserved output (fat's 10,000
visible allowance + the 16,000 hidden reserve) `= 282,477 < 320,000` (`SMALLEST_POOL_BUDGET_TOKENS`).

## What we want from you

A verdict — **APPROVE / APPROVE-WITH-ITEMS / REVISE** — plus findings. Verify what you can against
the repo and say explicitly when a claim checks out; we would rather absorb a correction now than
discover it at a paid calibration call. Then these seven, in roughly descending order of how much
the answer would change:

1. **Is the thin prompt's recall instruction safe at N > M?** This is our top concern. The prompt
   says retain everything plausible, when in doubt retain, precision is stage 2's job — and then
   "stop at the limit the USER message states; if more identities than that are plausible, keep the
   most plausible ones." At today's scale (largest domain 51 < 100) the cap never binds and
   retain-all masks any defect. Post-ingest at ~490 identities against 100 it binds on **every**
   call, and a model that reads "retain generously" and then truncates by position rather than by
   judgment produces *silent, unrecoverable* candidate loss — entities never reach stage 2 and
   nothing reports their absence. Does this prose invite that? Is the two-clause structure (retain
   generously / then rank and cut) the wrong shape, and if so what shape survives the transition?

2. **Is the fat prompt underspecified on ranking?** It says "rank the entities relevant to the
   QUERY, best first" and gives relevance-not-identity guidance with one worked case, but states no
   ranking criterion. **precision@5 is the project's only normative gate** (spec §8.3 metric 3), so
   the top-5 ordering is what gets scored. Does the prompt need explicit ranking guidance, and can
   it get it inside 691 B?

3. **Does naming `max_results` invite padding to the cap?** We render it because the validator counts
   `over_cap` as an attempted violation and charging a selector for a rule it was never told is a
   measurement of our own omission. The countervailing prose is "an empty `selections` list is a
   correct and expected answer … padding it with weak matches is a defect." Is that enough, or does
   stating a number dominate?

4. **The excerpt-honesty clause** — "an excerpt is the opening of the entity's body, so absence of a
   topic from an excerpt is weak evidence about the entity as a whole; a title-only entry has no
   excerpt at all and is judged on its identity line." True (policy v1 takes a leading ~250-word
   excerpt), and it exists to stop false negatives from a truncated body. Does it instead license
   over-selection on thin evidence?

5. **Is 691 B enough headroom, or is the system block already too thin for the task?** If the prose
   needs more than that, say so plainly — raising `SYSTEM_TEMPLATE_BUDGET_BYTES` edits a ratified
   §7.0a figure and costs a blueprint v0.15 bump. That is an expected cost, not a regression, and we
   would rather pay it than ship an under-instructed selector.

6. **Are the unindented `EVIDENCE:` / `QUERY:` section headers a strong enough boundary?** Given
   H04, adversarial content *can* currently forge an unindented line via a title. Options we see:
   fix `render_thin_line` (a byte change to golden-pinned P1 code), use a harder-to-forge delimiter
   in the templates, or leave it and rely on the H-class fixtures. Which, and why?

7. **Mechanics, anything wrong rather than differently-decided:** the single-pass substitution as a
   P10 control; both silent-failure guards (unknown slot raises, unused value raises); the digest
   taken over loaded *text* so a CRLF checkout cannot move it; `repo_path` as a literal because
   `relative_to(repo_root)` raises under an installed layout; the `prompts.py` vs `prompts/`
   name collision relying on module-beats-namespace-package precedence; and whether
   `test_prompts.py` actually pins what its docstrings claim — particularly the
   schema-example-through-the-real-validator tests, which are the only oracle prompt prose has.

Findings that make a claim about the code should name file and line. If you conclude the prose is
fine as-is, say that explicitly — "no change" is a useful answer here and we will not read silence
as approval.
