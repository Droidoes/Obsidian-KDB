## 1. Substantive: §2.3's strict fail-closed contradicts the project's ratified coerce-don't-reject principle — and contradicts §2.3's own stage-1 rule

C4 hardened validation so that **any** of six violation classes invalidates the entire selector response and
fires the deterministic fallback. For *identity* breaches that is exactly right, and codex's F6 objection to
keep-the-good-entries partial acceptance is well taken. But two of the six classes are not identity breaches:

- **class 4, duplicate slug**
- **class 5, over-cap (`len(selections) > max_results`)**

These are textbook **benign over-supply**. The project has a ratified rule for precisely this
(`feedback_coerce_dont_reject`): LLM over-supply / out-of-range / missing-nullable → *normalize*, do not mark
invalid; reserve rejection for unrecoverable content. And #119 — which this spec cites approvingly as the line
it is holding — ratified the governing formulation: **reject ambiguity, not harmless representational
differences.** A duplicate slug is not ambiguous; dedupe it. An over-long list is not ambiguous; truncate it in
returned order. A *foreign* slug is an identity breach and must reject.

**The spec already agrees with me — one paragraph later.** §2.3's stage-1 rule reads:

> "**Single pragmatic exception:** stage-1 over-cap (>M retained) is **truncated to M in returned order** with
> typed telemetry, not treated as a violation."

So the same deviation class is coerced at stage 1 and rejected at stage 2, and the harsher treatment lands on
the path that carries the actual result. That asymmetry has no stated justification.

**Why this matters beyond tidiness — the fallback is a no-op for the motivating class.** Under §3.4 the fallback
is exact/alias resolution of the expressions, and `warren-buffett` resolves to nothing (no such node — #122
finding 4). So **every fallback is a silent reversion to pre-#123 behavior for exactly the case #123 exists to
fix.** Under C4 as written, a selector that emits one duplicate slug in an otherwise perfect ten-hit response
loses all ten and the source gets empty T2. With a cheaper selector model that is not a hypothetical.

**Proposed change to §2.3** — split the six classes by kind:

| class | kind | disposition |
|---|---|---|
| 1. invalid JSON shape | unrecoverable | fail-closed → fallback |
| 2. foreign slug | **identity breach** | fail-closed → fallback |
| 3. unknown `matched_expression` | ambiguous attribution | fail-closed → fallback |
| 4. duplicate slug | benign over-supply | **coerce**: dedupe, keep first occurrence, typed telemetry |
| 5. over-cap | benign over-supply | **coerce**: truncate to `max_results` in returned order, typed telemetry |
| 6. malformed expression accounting | ambiguous | fail-closed → fallback |

Coerced responses remain **honest partials**, not failures; the attempted-violation rate in §6.3 still records
class 4 and 5 occurrences, so selector compliance stays measurable (codex F7's point survives intact — the
metric is on *attempted* deviations, and coercion does not hide them). This also brings stage 1 and stage 2
under one rule instead of a stated exception.

**If Joseph prefers to keep C4 strict as written**, then the compensating control is §2 item 1 below: fallback
rate must become a hard gate, because strictness converts selector noise directly into status-quo reversion.

## 2. Minor items

1. **Fallback rate is only "watched," and it should be a hard gate (§8.4).** §8.3 lists "fallback-mode rate +
   fallback ordering correctness" in the plus-list; §8.4's hard gates do not include it. Given §1 above — every
   fallback is status-quo behavior for the motivating class — the fallback rate *is* a measure of whether #123
   is delivering. A predeclared ceiling belongs beside the person-class recall gate.
2. **Cap-induced `unresolved_expressions` confounds abstention accuracy (§2.3 rule 6 ↔ §8.3 metric 6).** Rule 6
   requires every request expression to be accounted for as matched **or** unresolved. If a source emits more
   expressions than `max_results` can serve, expressions with genuinely relevant entities land in
   `unresolved_expressions` because of the cap, not because nothing is relevant — and semantic abstention
   accuracy (class E) then scores a cap artifact as an abstention judgment. Either carry a reason on unresolved
   entries (`no_relevant_entity` vs `cap_exhausted`) or state `max_results` for pass-1.5 and show it comfortably
   exceeds typical expression counts. Related: `max_results` is described only as "the T2 budget" (§1.1) and is
   never given a value.
3. **`identity_match_annotations` on fallback hits are trivially true, which confounds the exact_matchable
   delta (§8.3).** Fallback hits are produced *by* the exact/alias resolver, so `exact_matchable` is true by
   construction. The "what the LLM adds beyond string matching" metric must be computed over
   `selected_by: llm` hits only. One clause in §8.3.

  #75 itself.

because it changes the contract's failure semantics and therefore the test plan in §9.
