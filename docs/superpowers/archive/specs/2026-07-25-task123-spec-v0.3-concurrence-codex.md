## R1 — CONCUR-WITH-ITEMS

Per-entry salvage preserves the D9 output invariant. My whole-response
fail-closed preference remains dissent-for-record.

The compensating controls have one gap: a parseable but structurally unusable
response—such as `{}` or `{"selections": "invalid"}`—has no entries to
salvage but is not `unparseable_response`. Likewise, a response whose entries
are all dropped currently records neither selector failure nor semantic
abstention reliably. Escaped identities and selector-failure gates could both
pass.

Add:

- `structurally_unusable_response` as a retryable response-level failure;
- an `all_entries_dropped` rate and gate, or classify it as retryable failure;
- an explicit `valid_entry_yield` value for zero returned entries.

See spec §2.3 and §8.4.

## R2 — CONCUR-WITH-ITEM

The uniform 80% pre-flight rule is sound. However, the proposed
`words × 1.3` fallback is demonstrably not conservative for slug-heavy input:
the measured thin block estimates to about 2.2k tokens by words versus 3.8k
by characters.

Use the model tokenizer where available; otherwise use a genuinely safe
UTF-8-byte or empirically calibrated upper bound. An underestimated guardrail
can authorize a request it was intended to block.

## R3 — CONCUR

The narrower posture—"spec design approved; evaluation substrate open"—and

labels, and gates is clear. See spec §8.1.

## R4 — CONCUR-WITH-ITEM

The claim that Stage 1 is non-binding whenever `N ≤ M` is currently false. A
recall-oriented prompt can still omit identities when only 51 are supplied;
validation cannot distinguish omission from judgment. Consequently, results
are not guaranteed to equal a fat-only call, and Stage-1 recall can fail
before a domain exceeds 150.

To make R4's premise true, the controller should enforce:

```text
if eligible_space_size <= M:
    effective_retained = every eligible identity
```

The thin response may still provide ranking for concordance instrumentation.
This preserves always-two-stage execution while preventing small-space
candidate loss.

See spec §2.1 and §7.2 R4.

## Result-state correction

`status` omits `budget_exceeded`, and `execution: not_executed` is inaccurate
after failed thin/fat attempts. Use, for example:

```text
status:
  completed | abstain_empty_space | budget_exceeded | selector_failure

execution:
  not_executed | thin_attempted | two_stage_attempted
```

The audit trace can separately identify completed stages.

Finally, vision v1.4 still says "one source = one batched call" and mentions
routing "single-stage → two-stage → fail," both contradicted by R4. See vision
§3 and P1.
