Obsidian-KDB Architecture Tutorial

GraphDB-KDB: the queryable memory behind the compiled knowledge base

GraphDB-KDB is the Kuzu-backed ontology layer for Obsidian-KDB. The Markdown wiki is the readable surface; the graph is the live structure that stores entities, sources, links, provenance, domains, aliases, and eventually belief-revision claims.

1. Mental Model

The project is best understood as a raw-text to knowledge-graph compiler. One conductor — kdb-orchestrate — walks each source through Pass-1 enrichment, Pass-1.5 semantic graph search, and Pass-2 compile; the model emits structured page intents, Python validates and canonicalizes them, writes Markdown for Obsidian, and syncs the same structured result into GraphDB-KDB — all inside one per-source commit transaction.

The system is multi-pipeline by design: a hand-authored registry, KDB/state/pipelines.json, declares which ingestion pipelines exist and what each one scans (root + excludes + globs). The standing production pipeline scans the Obsidian vault in place — sources are enriched where they live. What used to be the KDB/raw/ boundary is now just a convention for pipeline roots, not a special mode; new pipelines (a prompt archive, a filtered Substack email flow) are registry entries, not code.

Core distinction: Obsidian is the IDE and human-readable rendering. GraphDB-KDB is the queryable memory of relationships.

3. Components

Schema

schema.py defines Kuzu node and relationship tables plus migrations — currently v2.5 (Entity, Source, Domain, PendingLink, Claim; nine edge tables).

Connection manager

graphdb.py opens Kuzu read-write (bootstraps + migrates schema) or read-only (read_only=True, never migrates, writes raise GraphDBReadOnlyError).

Graph write engine

intake.py applies one compile result into Kuzu inside the per-source commit transaction — entity upserts, SUPPORTS replace, drain-as-you-go LINKS_TO with the durable PendingLink ledger (#136), per-source SUPPORTS-diff deprecation (#130), domain re-derive, alias materialization.

Adapter

adapters/obsidian_runs.py is the replay path: it translates run journals + sidecars from state/runs/ back into the same intake calls during graphdb-kdb rebuild. (Live compile-sync has gone straight to intake since #91.)

Queries

queries.py answers graph questions: what is near this entity, what links into it, what route connects two entities, which sources support it, alias-aware canonical resolution, KPI primitives, and a custom Cypher escape hatch.

Analytics

analytics.py computes graph-level signals: central entities with PageRank, clusters with Louvain community detection, and weak bridges with structural-hole detection.

Verifier and rebuilder

verifier.py and rebuilder.py are the recovery proof: replay eligible run journals into a clean Kuzu graph, then diff replay vs live across three layers (source-state preflight, canonicalization invariants, full structural diff).

CLI

cli.py powers the graphdb-kdb command-line interface — 15 subcommands (see §9).

MCP server

kdb_mcp/ — read-only FastMCP stdio server (kdb-mcp-server): 7 tools over the live graph, each call reopening the graph read-only. This is the surface LLM clients (and the future FTS tool, #142) plug into.

Snapshot

snapshot.py — atomic, write-only JSONL export (format v7) with a checksummed manifest, under state/graph-snapshots/.

Parked 2.0 tier

ops/op_1_promote.py + core/belief_classifier.py — the O1 hypothesis-promotion pipeline and belief classifier. Built, tested, and deliberately unwired (#139 tracks the wire-up decision).

4. Graph Basics

A Kuzu GraphDB is easiest to picture as a property graph with three pieces: nodes, edges, and properties. Nodes are the circles, squares, triangles, or other objects. Edges are the labeled lines between them. Properties are the data attached to either nodes or edges.

Source: raw input file Entity:summary — top-level distillation (1 per source) Entity:article — synthesized long-form piece Entity:concept — individual idea or concept Domain: classification bucket

Node

A node is one stored object in the graph. Node types are the graph equivalent of classes in the schema: Entity, Source, Domain, and the edge-less PendingLink ledger (plus the parked Claim table). Each type has its own allowed properties.

Connection

A connection is always between two nodes. The two nodes can be the same type or different types, but only if the schema allows that edge type. For example, rationality is an Entity node whose page_type is concept. If it links to mungers-four-levels-of-rationality, another Entity node, the graph-write code creates a LINKS_TO edge between them. If a raw source supports rationality, that is a SUPPORTS edge from a Source node to an Entity node.

Edge

An edge sits between two nodes. It does not live "on" either node. It is a separate relationship record with a start node, an end node, a type, and optional properties like run_id or created_at. The Markdown wikilink [[mungers-four-levels-of-rationality]] becomes a LINKS_TO edge from the page containing the wikilink to the page being linked.

Properties

Properties are data fields attached to nodes or edges. A node property might be Entity.slug = "rationality" or Entity.page_type = "concept". An edge property might be LINKS_TO.run_id, which records which compile run created that relationship.

Other Terms

  • slug: stable ID for an entity.
  • canonical_id: alias/canonicalization pointer; null means self-canonical.
  • neighbor: query result for a node reached by following one or more edges.
  • depth: number of hops to traverse.
  • subgraph: selected nodes plus the selected edges among those nodes.
  • provenance: standard data/knowledge-graph term for origin or evidence trail. In this tutorial, it means source-to-entity support metadata: "which source produced or supports this entity?"
  • deprecated: an entity whose last SUPPORTS edge was dropped by the model — invisible to all readers, revivable on re-emit (#130; supersedes the old "orphan" concept, which no longer exists: a deleted source's sole-supported pages are erased outright).
  • community: an algorithmically detected cluster with denser internal links than external links.
  • structural hole: a weak bridge between communities.

5. Current Schema (v2.5)

Obsidian's graph view can feel like one kind of node connected by one kind of line. Kuzu is a typed graph: nodes have different types, and only schema-declared edge types can connect them. The visual picture is still a mesh, but the mesh has labeled node classes and labeled relationship classes.

Each generated page is one Entity node with a page_type field that distinguishes its role. Each raw source is one Source node. A source connects to every page it produced through SUPPORTS edges. Pages connect to each other through LINKS_TO edges — the graph form of Markdown wikilinks. One ledger table, PendingLink, records links whose target slug does not exist yet (#136); it has no edges of its own. 

-- 2.5 schema (current) --
Source  --SUPPORTS-->  Entity  --LINKS_TO-->  Entity
Entity  --BELONGS_TO-->  Domain
Entity  --ALIAS_OF-->  Entity   (alias → canonical)
PendingLink            (edge-less durable ledger: source_slug → target_slug)

-- parked 2.0 claim layer (tables exist, unwired, always empty) --
Source  --EVIDENCES-->  Claim  --ABOUT-->  Entity
Claim   --SUPERSEDES / CONTRADICTS / QUALIFIES-->  Claim

Version arc (schema.py module docstring): 1.0 baseline → 2.0 canonical_id + ALIAS_OF → 2.1 Domain + BELONGS_TO → 2.2 Claim layer → 2.3 Source summary/author/domain → 2.4 derived BELONGS_TO (destructive — rebuild required, no 2.3→2.4 migration) → 2.5 PendingLink (non-destructive ADD, #136).

Edge types

LINKS_TO Entity → Entity Intake (code) LLM writes [[slug]] in page body; code materializes each wikilink as an edge inside the same per-source commit transaction (#136 drain-as-you-go). Targets that don't exist yet go to PendingLink instead.

The important shift: an edge is not a property of a node. It is its own typed record. That is what lets queries ask directly: "which sources support this entity?" or "which entities point into this one?"

What a node stores (and what it doesn't)

The graph is a topology + metadata projection — it records what exists and how it connects, not the prose. The full page body is not stored on the node. It lives in two canonical homes, reached by slug:

  • KDB/wiki/ — rendered Markdown pages (human-readable)
  • KDB/state/compile_result.json + per-run sidecars — full page output: body, outgoing_links, title, confidence (machine-readable)
NodeStored on the nodeExternalized
Entity slug, title, page_type, status (active | deprecated | alias), canonical_id, run-tracking timestamps. (confidence still exists in DDL but is a dead column — never written since #115.) body (→ wiki / compile_result); outgoing_links (→ LINKS_TO edges)
Source source_id, canonical_path, hash, source_type, summary, author, domain, ingest lifecycle (ingest_state, ingest_count, first/last_seen_at, moved_to, …) —
Domain name, created_at, first_run_id —
PendingLink link_id (source_slug|target_slug), source_slug, target_slug, first/last_run_id, timestamps — (no edges — it is a ledger row)
The rule is a gradient, not a binary: titles and short summaries in, full bodies out. Source.summary is a short summary kept on the node on purpose. Bodies stay external because graph engines are tuned for pointer-chasing across relationships (not blob storage), and the body should have one canonical home so no copy can drift. A consumer needing body-at-the-node does a second lookup by slug — cheap at this scale. See docs/reference/graph-nodes-edges-logic.md for the full rationale and the per-node property lists.

2.0 Claim layer (schema present, pipeline parked)

The 1.0 graph records structural topology: entities exist, sources reference them, concepts link to concepts. It does not record what a source asserts about an entity — only that the entity appears in it. The 2.0 Claim layer adds propositional knowledge, and its tables have existed in the DDL since schema v2.2: 

-- 2.0 claim layer (in DDL, production-empty) --
Source  --EVIDENCES-->  Claim  --ABOUT-->  Entity
Claim  --SUPERSEDES / CONTRADICTS / QUALIFIES-->  Claim

The machinery is built but parked, unwired: kdb_graph/ops/op_1_promote.py (O1 hypothesis-promotion pipeline, #83/#84) and kdb_graph/core/belief_classifier.py (stateless deterministic classifier) are imported only by tests — no production path writes a Claim row, so production graphs always report claims: 0. Wiring it is a deliberate future decision (tracked under #139's use-case pick); the 2026-08-08 analytics gate on the maiden graph (737 cross-community bridges, 562 interpretable communities) says the structural layer is healthy enough to support it. See docs/2026-08-07-graphdb-utilization-and-kuzu-landscape.md.

6. How GraphDB Is Populated

The conductor is kdb-orchestrate. Per source, in one continuous loop:

  1. Scan — walk the pipeline root from pipelines.json, hash each file, diff against the manifest (no LLM).
  2. Pass-1 enrich — cheap LLM call classifies the source (signal/noise, domain, source_type, summary, entity keys) → embedded as YAML frontmatter. Noise sources stop here (frontmatter + manifest row only).
  3. Pass-1.5 semantic graph search (#123, kdb_search) — a selector LLM picks the existing entities relevant to this source from the graph-materialized domain space; a search envelope is archived per source.
  4. Pass-2 compile — the extraction LLM reads the source plus a graph-derived context snapshot (T1/T2/T3 tiers; T2 = the pass-1.5 selector's hits) and returns structured JSON page intents.
  5. Gauntlet — proposal-schema gate → normalization bridge (#119) → canonical-schema gate → canonicalize (alias ledger).
  6. Commit (β order) — page_writer writes the wiki pages → the graph intake runs in the same per-source Kuzu transaction (entity upserts, SUPPORTS replace, drain-as-you-go LINKS_TO with PendingLink upserts, per-source SUPPORTS-diff deprecation, domain re-derive, alias materialization) → manifest write LAST (the commit boundary).
  7. End of run — reconcile MOVED/DELETED (a deleted source's sole-supported pages are erased: node + file), a slim finalize (deprecation convergence + combined compile_result.json), then replay journals + sidecars archived under state/runs/.
Plain version of the adapter boundary: the live path writes through kdb_graph.intake.apply_compile_result directly inside the orchestrator's commit transaction (since #91 — no adapter involved). The ObsidianRunsAdapter exists for the replay path: graphdb-kdb rebuild walks state/runs/ journals and the adapter translates each producer-shaped journal back into the same intake calls. Producer logic never mixes with graph-storage logic in either direction. 
live:    page intents ──> intake.apply_compile_result (per-source txn) ──> Kuzu records
rebuild: state/runs/<run_id>.json + sidecars ──> ObsidianRunsAdapter ──> same intake calls

7. Capabilities

  • Lookup central concepts via PageRank, which ranks entities by graph importance based on incoming and outgoing link structure.
  • Traverse nearby concepts with directed or bidirectional neighbors. A neighbor is reached by following edges from a starting node.
  • Find incoming references to a concept. An incoming reference is another entity with a LINKS_TO edge pointing into the current entity.
  • Find shortest paths between entities. A shortest path is the minimum number of edge hops between two nodes, subject to direction and max-hop settings.
  • Extract all entities created from a source through SUPPORTS provenance edges — and the reverse: which sources currently support an entity.
  • Inspect a source-specific subgraph: the selected source's supported nodes plus links among those nodes.
  • List deprecated entities (#130 lifecycle): pages the model dropped, which lose their last SUPPORTS — revivable on re-emit, erased only when their source is deleted. (The old "orphan candidate" class is gone; zombies are structurally impossible.)
  • Browse domains and their entity counts (graphdb-kdb domains).
  • Inspect the PendingLink ledger (#136): forward links waiting for their target slug to arrive — drained automatically when it does.
  • Detect topic communities with Louvain clustering: groups of entities that link more densely to each other than to the rest of the graph.
  • Detect structural holes between communities: sparse bridges where a missing concept or source might improve the knowledge structure.
  • Semantic graph search (kdb_search, #123): two-stage LLM selection over the graph-materialized space — the pass-1.5 consumer already seeds every compile's T2 context; a CLI/MCP human query surface is a planned later track.
  • Serve the graph to LLM clients over MCP: kdb-mcp-server exposes 7 read-only tools (get_entity, graph_neighborhood, find_path, sources_for_entity, entities_for_source, resolve_search_keys, get_body), each reopening the graph read-only per call — full treatment in §10.
  • Rebuild from run history (journals are the source of truth; the graph is derivable).
  • Verify live graph against replayed graph (three layers: source-state preflight, canonicalization invariants, full replay diff).
  • Snapshot graph state into diffable JSONL backup (format v7, write-only).

8. Build And Populate

Install the project in editable mode:

cd ~/Droidoes/Obsidian-KDB
pip install -e ".[dev]"

The graph lives at <vault>/KDB/graph — OBSIDIAN_VAULT_PATH (default ~/Obsidian) drives both content and graph location; KDB_GRAPH_PATH overrides the graph alone. Schema auto-creates on first write-open, so explicit init is rarely needed: 

graphdb-kdb init

Populate through the normal orchestrated pipeline (one pipeline per invocation):

kdb-orchestrate --vault-root <vault> --pipeline <id>
# standing production model: deepseek-v4-flash; override with --model / --selector-model

Erase all derived state (wiki tree, graph, manifest, alias ledger) — wipe-only, always requires typed confirmation, journals archived to state/pre-wipe-runs/ first:

kdb-orchestrate --vault-root <vault> --wipe

Rebuild the graph from historical run journals:

graphdb-kdb rebuild --vault-root <vault> --yes

Verify the live graph (replay-to-temp structural equality):

graphdb-kdb verify --vault-root <vault>

Snapshot the graph:

graphdb-kdb snapshot --vault-root <vault>

Serve the read-only MCP stdio server (7 tools) to an LLM client:

kdb-mcp-server
Operational note: avoid running multiple graphdb-kdb commands in parallel against the same Kuzu file. Kuzu can reject concurrent opens with a file-lock error. (Read-only opens — stats, neighbors, the MCP server — are safe to mix; keep writers single-file.)

graphdb-kdb communities

graphdb-kdb structural-holes

graphdb-kdb domains

graphdb-kdb subgraph-by-source "Value Investing/Buffett Munger/Buffett_on_Stock_Ownership.md"

graphdb-kdb cypher "MATCH (e:Entity) RETURN e.slug, e.page_type ORDER BY e.slug LIMIT 10"

graphdb-kdb cypher "MATCH (p:PendingLink) RETURN p.source_slug, p.target_slug LIMIT 10"

10. MCP — the Graph as an Agent Tool Surface

The graph is not only a pipeline artifact and a CLI surface — it is a tool surface for LLM clients. kdb_mcp/ is a read-only Model Context Protocol (MCP) server (FastMCP, stdio transport): the client spawns it as a child process, and from then on the agent asks the knowledge base structural questions as native tool calls instead of shelling out to graphdb-kdb: 

kdb-mcp-server          # stdio; also: python -m kdb_mcp.server

Design rules

  • Read-only by construction. Every tool opens the graph with read_only=True (writes raise GraphDBReadOnlyError) and re-opens per call, so a long-lived server always sees fresh state after a pipeline run. Read-only opens are safe to mix with a running pipeline — the single-writer rule applies to writers, not readers.
  • Same paths as everything else. The graph resolves via KDB_GRAPH_PATH, else <vault>/KDB/graph; page bodies resolve via OBSIDIAN_VAULT_PATH — one env var points the server at the production vault or the sandbox.
  • Stable response shapes. Tools return Pydantic models from kdb_mcp/models.py — public cards, not internal kdb_graph dataclasses — so the wire contract survives internal refactors.
  • Structure first, text on demand. Six tools answer graph questions; only get_body reaches into the vault for page prose (frontmatter stripped). Clients walk structure cheaply and pay for text only when they need it.

The 7 tools

ToolQuestion it answersReturns
get_entity(slug)What is this node?EntityCard — slug, title, page_type, status, canonical_id (non-null ⇒ alias)
graph_neighborhood(slug, direction, depth)What sits near this concept?Neighborhood — EntityCards within N LINKS_TO hops (out | in | both)
find_path(from_slug, to_slug, max_hops)How do two ideas connect?PathResult — shortest directed LINKS_TO path + hop count
sources_for_entity(slug)Where did I learn this from?EntityProvenance — SourceCards (source_id, source_type, domain, status) currently SUPPORTS-ing it
entities_for_source(source_id)What did this source contribute?SourceProvenance — EntityCards the source currently supports
resolve_search_keys(keys)"Warren Buffett" → which slug?SearchKeyResolution — alias-aware resolved map + unresolved list
get_body(slug, page_type)Read the page itselfBodyResult — wiki page prose, frontmatter stripped; page_type ∈ summary | concept | article

A typical agent session: resolve_search_keys(["margin of safety"]) → graph_neighborhood("margin-of-safety", depth=2) → get_body(...) on the two or three most promising hits — the same retrieval pattern a human follows with the §9 commands, but expressed as tool calls the client can chain autonomously.

  "mcpServers": {
    "kdb-graph": {

Where this goes next: the semantic graph search (#123) currently serves only the pipeline (pass-1.5); a human/agent query surface over MCP is its planned later track, and the FTS work (#142) would land here as an additional tool — full-text over page bodies, joined with the structural tools above.

11. Practical Use Cases

Compile context

Live since #123: pass-1.5 semantic graph search picks the relevant existing entities for every source before Pass-2 — two-stage LLM selection over the domain subtree, archived per source under state/runs/<run_id>/search/. This card used to be the aspiration; it is now the pipeline.

Knowledge-hole detection

Use weak inter-community bridges to identify missing concepts that could connect topic clusters.

Learning paths

Start from a concept, traverse neighbors, then expand through communities.

Source audit

Ask which entities a source contributed and which relationships were created from it.

Concept provenance

Ask which raw sources currently support a concept.

Belief revision

Use the claim layer to track when new information reinforces, qualifies, contradicts, or supersedes prior beliefs. Parked: the O1 promotion pipeline + belief classifier exist under kdb_graph/ops/ + kdb_graph/core/ but are unwired — the maiden graph's analytics gate (2026-08-08) says the structural layer is ready when we choose to wire them (#139).

Model evaluation

Evaluate whether a compile result integrates into the existing graph or creates disconnected islands.

Relationship search

Search over structure and provenance instead of only matching text.

Summary

GraphDB-KDB is the system's memory of relationships. It stores the ontology that the compiler builds from raw text, while Obsidian Markdown gives that ontology a readable surface. The value is not the graph visualization; the value is queryable structure, provenance, verification, and adaptive learning workflows on top of that structure.
