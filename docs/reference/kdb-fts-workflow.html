1The big picture

kdb_fts (Task #145) is a parallel extraction/ranking system over the gmail-substack raw corpus: ~2,659 newsletter articles Joseph cannot read by hand. It is a deliberate architectural competitor to the GraphDB pipeline — same raw sources, different extraction philosophy, head-to-head comparison planned. The founding decision (D1): extract once into structured, source-grounded records; rank deterministically many times. FTS5 is a read surface, never the core. The corpus is information, not knowledge — majority politics/geopolitics by volume (~55%), investment-named ~17% — so a cheap gate keeps the idea/lesson ledger unpolluted (D5), and Joseph's own judgments, captured as immutable events (D13/D18), calibrate everything to his usefulness.

End to end: Gmail → feeder → raw corpus → deterministic intake (ledger + FTS5) → LLM gate → the review loop (freezer → web app → feedback events → calibration) → planned extraction, ranking, and queue kinds. Phase 5 (steady state: incremental intake/gate/extract on new feeder files, export, calibration proposals after ~200 events) is the ongoing tail of the same loop.

Why this shape

  • Cheap gate, deep extraction (D5) — one ~cheap LLM verdict per article; deep extraction only for eligible buckets. The politics majority never pollutes the idea/lesson ledger.
  • Extract once, score many (D14) — ranker weights are versioned JSON; re-weighting never re-extracts.
  • Joseph's labels are ground truth for personal usefulness only (D8) — faithfulness, correctness, and track record are separate axes, never one "quality" score.
  • Feedback is the irreplaceable asset (D18) — everything else is rebuildable or replayable; feedback/events.jsonl is neither.
  • Hard write boundary (D3) — kdb_fts reads the raw tree; every write is confined to <vault>/KDB/fts/, enforced by a guard test, not convention.

The frontmatter contract (what intake later reads)

Every converted source starts with YAML frontmatter:

  • title, author, published_date, source_url
  • gmail_message_id — this becomes the article's stable identity downstream (D17)
  • content_kind — article | video | podcast (drives the media skip-by-rule, D16)
  • feeder: gmail-substack, ingested_at

The promo prefilter (already applied to the backlog)

The one-off scripts/gmail_promo_prefilter.py (2026-08-15) tuned the marker battery over the 4,189-file converted corpus — three report-only iterations, Joseph-eyeball-gated — then --apply moved 1,530 promo/truncated files (36.5%) into _promo/ (move log: _promo/_movelog.jsonl). 5Phase 0 — Intake & the ledger BUILT

Deterministic walk of the raw tree into a SQLite ledger plus a full-text search surface — no LLM calls, no cost. Idempotent: re-running on an unchanged tree is a no-op. This is where the corpus becomes addressable state.

Key components

ModuleRole
kdb_fts/intake.pyscan_tree (pure: walk, classify, no writes) + run_intake (upsert, prune absent, FTS rebuild)
kdb_fts/ledger.pyTyped DB access — the only module that opens ledger.sqlite (write-boundary guard)
kdb_fts/schema.pyDDL + numbered migrations (txn-wrapped; SCHEMA_VERSION = 2 after Phase 1)
kdb_fts/state.pyState-root resolution: $KDB_FTS_PATH else <vault>/KDB/fts (D4)
kdb_fts/author_map.pyRaw author string → canonical author/publication via Joseph-editable author_map.yaml

Identity & classification rules

  • Stable identity (D17): article_id = gmail_message_id from frontmatter, else "sha256:" + sha256(file text) — never the file path. A move keeps the id; path is a mutable attribute.
  • Cleanliness — exactly one label per file, precedence digest-stub > media > bleed > short > ok: digest stub = and N more title pattern; media = content_kind ∈ {video, podcast}; bleed = unparseable frontmatter (repaired view — original bytes untouched); short = body < 50 words.
  • Paragraph IDs: blank-line split; paragraph i becomes p0001…, stable within one content hash. Paragraphs are replaced only when the hash changes.
  • FTS5: full repopulation from articles + paragraphs on every intake (cheap at 4.2M words); the author column indexes the canonical name, falling back to raw (Phase-1 fix).

6Phase 1 — The gate BUILT LIVE RUN IN PROGRESS

One cheap deepseek-v4-flash JSON-mode call per ok-cleanliness article (blueprint §7.2, D5). The gate decides what an article is and whether it deserves deep extraction — so the expensive Phase-2 pass never touches the politics majority. The gate is reversible and logged: kdb-fts promote (planned) can force any article past it.

The gate pipeline (kdb_fts/gate.py): pure prompt/parse half + the run_gate runner (DB + call_model + journal). Resumable: an article with a verdict at the same (model, prompt_version) is skipped — re-gating means bumping gate_v1.

The verdict (what the model returns)

  • topic — one of 6 closed labels (gate.TOPICS): investment · finance-econ · geopolitics · china-econ · ai-tech · other. Unknown labels fail closed to other + both extract flags false; the raw label is kept for the journal.
  • signal 0..1 — information density for an investor (specificity, argument quality, conviction backed by reasoning).
  • extract_ideas / extract_lessons — eligibility booleans. Both false is a normal answer — the prompt says most articles deserve neither.
  • confidence (nullable, clamped 0..1) + one-line rationale (≤280 chars).

Input: title + author + published_date + body truncated at MAX_BODY_WORDS = 4000 (~p95 body length is 4,245 words). Prompt template: kdb_fts/prompts/gate_v1.md (version == filename stem).

The exploration sample (the gate's honesty mechanism)

Each gate pass marks a fixed 5% exploration sample (minimum 10, capped at population) of ineligible articles, stratified by author — deterministic: groups sorted by (−size, author), ids sorted, round-robin (gate._exploration_sample). Those rows get exploration = 1 in gate_verdicts and are extracted anyway in Phase 2, so the gate's false-negative rate is measured, not hoped (blueprint §7.2).

Skip-by-rule classes (media, short, digest-stub, bleed) are never sent to the LLM (D16) — only the 2,511 ok articles are gated.

gate_verdicts (migration 2)

One row per (article_id, run_id): topic, signal, extract_ideas, extract_lessons, confidence, model, prompt_version — plus three additive columns beyond blueprint §6's list (Phase-1 plan deviation 1): exploration (home for the 5% sample), input_tokens / output_tokens (so status reports cost-to-date without parsing journals), and rationale. Latest verdict routes; history is kept (ledger.latest_verdicts = each article's verdict from its latest run).

Cost reality check (Phase-1 plan deviation 7) Blueprint §11 estimated the full-corpus gate at < $0.5 — computed at the old flash price (0.14/0.28). At the 2026-08-16 peak cache-miss rates (0.44/1.32) the real figure is ≈ $2–3 (commit 7b5fc64). Still trivial; noted so the live gate's reported cost isn't a surprise. --dry-run performs the LLM calls but commits nothing — no verdict rows, no exploration marks, no journal (D20).

7The freezer — review/<batch_id>.json BUILT

The freezer (review.py::freeze_batch) picks a deterministic stratified sample of gated articles and freezes it to <vault>/KDB/fts/review/<batch_id>.json. The frozen payload is exactly what the web app renders — and it is the exposure record (D13/D22): every feedback event from that batch is stamped with the position and score the frozen JSON says Joseph saw. A frozen batch is never overwritten — freeze_batch raises FileExistsError on an existing path.

How the sample is drawn (review._stratified_sample)

  • Stock: every article with a gate verdict (ungated articles are not calibration stock), joined to its latest verdict's topic, signal, and exploration flag, plus the full body from paragraphs.
  • Topic-proportional allocation across the 6 topic strata, minimum 2 per stratum where stock allows.
  • Even-spacing within each topic, ordered by (author, published_date, article_id) — spreads authors and dates deterministically; then a deterministic trim/backfill to exactly n (default 150 for calibration-p1).
  • Payload: batch_id, kind, created, ranker_version (null in v0 — no ranker yet), and items[] with position, title, canonical author, published_date, topic guess, signal, body, exploration flag.
Recorded blueprint deviations 8 & 9 (as-built wins) Deviation 8: stratification is topic-only. Blueprint §9's letter says "stratified by author, date, length, topic guess" — within each topic stratum, even-spacing over (author, published_date, article_id) spreads author and date, but length is genuinely unstratified: the calibration matrix may carry a length bias. Deviation 9: blueprint §7.5's "20% of batch slots reserved for exploration" is absent from freezer v0 — deliberate for calibration-p1 (calibration wants unbiased stock, and the gate-pass exploration sample is already marked in gate_verdicts); the quota arrives with queue-kind batches in Phase 4. Review v0 serves kind = calibration only (review.py _KINDS).
Where it sits in the workflow Freezing happens lazily: kdb-fts review --batch calibration-p1 freezes the batch if the JSON doesn't exist yet ("froze batch calibration-p1 (calibration, n=150)"), then serves it. Re-running the same command re-serves the same frozen batch — the sample can never drift between labeling sessions.

8The review web app BUILT

The v1 review surface (D22): a stdlib-only local server (http.server.ThreadingHTTPServer on 127.0.0.1, ephemeral port) serving one static page — kdb_fts/assets/review.html (98 lines, no JS framework, no build step, no new dependency). Joseph labels in the browser; every click writes back as an immutable feedback event. The app writes nothing else.

Freeze → serve → click → event. Exposure context is stamped server-side from the frozen batch on every write-back — the client cannot invent the score or position it was shown.

What Joseph sees and does

  • Per article: title, canonical author, published date, the gate's topic guess + signal, and the full body in a scrollable pane.
  • One-click buckets: strong / interesting / weak / noise (keyboard 1–4) — the D13 fast bucket sort, ≙ 3/2/1/0 usefulness.
  • A free-text reason box surfaces at the extremes (strong/noise) — "the extremes teach the rubric the most" (D13).
  • Event appends are serialized by a threading lock across handler threads; webbrowser.open launches the page; Ctrl-C stops the server.

9Feedback events — feedback/events.jsonl BUILT

Joseph's judgments are the system's irreplaceable asset (D18): rebuildable state (SQLite, scores) and replayable state (run journals) can be reconstructed — his labels cannot. One append-only JSONL file at <vault>/KDB/fts/feedback/events.jsonl; there is deliberately no update or delete path (feedback.py). Excluded from any wipe/rollback; backed up with the vault.

The event (feedback.append_event)

  • action — closed vocabulary: strong · interesting · weak · noise (article buckets ≙ 3/2/1/0), accept · reject (ideas, D21), helpful · not-helpful (lessons, D21), save · skip · wrong-extraction · promote-to-extract.
  • target_type — article | idea | lesson | author; target_id.
  • reason_text / reason_tags — optional; expected at the extremes (D13).
  • Exposure context (D13): ranker_version, score_shown, position_shown, batch_id, exploration — stamped from the frozen batch by the review server.
  • ts — local ISO timestamp.

Mechanics & the scripting path

  • Append = read + atomic rewrite via common.atomic_io (crash-safe, write-guard-clean; fine at Phase-1 scale — thousands of events, low MB).
  • CLI: kdb-fts feedback <target_type> <target_id> <action> [--reason txt] [--tags a,b] — for scripting; the web app is the primary surface (D22), markdown export a fallback.
  • Deviation 2 (as-built): events land in JSONL only in Phase 1. Blueprint §6's feedback_events SQLite mirror table arrives with the ranker that consumes it (Phase 3) — YAGNI until then.
Why "immutable" is load-bearing Calibration, the future ranker, and any "why was this ranked #3 last Tuesday?" audit all assume the event log is ground truth with its original exposure context. A mutable log would silently invalidate every learned weight. Rollback of a run = delete its runs/<id> subtree and replay-forward; feedback events are never rolled back (blueprint §5).

10Calibration — does the gate agree with Joseph? BUILT

The Phase-1 exit gate (blueprint §9): Joseph hand-labels 150 stratified articles in the app as batch calibration-p1, then kdb-fts calibration (calibrate.py) computes the confusion matrix of gate verdicts against his labels. Joseph sets the accept threshold after seeing the matrix — no invented number lives in the code.

How the matrix is built (calibrate.report)

AxisDefinition
Label-positive (Joseph)Latest bucket label ∈ {strong, interesting} for the article, from feedback/events.jsonl filtered to the batch (file order = ts order; latest wins)
Gate-positiveLatest verdict topic ∈ {investment, finance-econ} (calibrate.RELEVANT_TOPICS)
Outputtp / fp / fn / tn + precision / recall / F1 (null-safe) + a per-topic positive/negative split

Run it with kdb-fts calibration --batch calibration-p1. Labeled articles without a verdict are skipped (can't happen for frozen stock — the freezer only samples gated articles).

The fallback is priced in If the gate underperforms against Joseph's labels, the recorded fallback (blueprint §9 Phase 1) is extract-all: a ~$1–3 switch, because D5 (gate-then-extract) is a policy, not a structural commitment. The threshold Joseph sets is recorded in docs/TASKS.md; consuming it is the Phase-3 ranker's job.

11Phase 2 — Extraction PLANNED

Blueprint design only (§7.3, §9 Phase 2) — no code yet. One structured LLM call per gate-eligible article (plus the 5% exploration sample), producing zero-to-N idea_mentions and zero-to-N lesson_cards, each backed by validated evidence spans.

The contract

  • Faithfulness is a hard gate (D10): every substantive field carries an evidence span; a deterministic checker (spans.py) proves the exact_quote is a substring of the source paragraph. Insert is refused otherwise — the record fails, not the article; other valid records from the same article still land (per-record salvage).
  • Zero is success (D11): the prompt must say emitting zero mentions/lessons is correct; forcing a filled schema is a defect. A political essay must yield 0 ideas.
  • ticker only when the exact string appears in the source.
  • The extractor may downgrade an article to neither (logged); it may never silently upgrade a skip-by-rule file.
  • JSON-schema-gated response, schema_version stamped; raw + salvaged model output per article lands in runs/<run_id>/extractions/<id>.json (replayable).

Tables it will add (blueprint §6)

  • extraction_runs — run_id × article_id, schema version, model, tokens/cost/latency, status (ok/empty/failed/skipped/exploration). Re-extraction = a new run keyed by schema version + model + content hash (D14).
  • idea_mentions — what one article claims: company, ticker (nullable), stance (long/short/pass/watch/unclear), thesis, valuation_premise, catalyst, risks, horizon, expires_on, extraction_uncertainty.
  • lesson_cards — principle, context, reusable_application, failure_mode, lesson_type (framework/mental-model/mistake-postmortem/process/risk/behavioral).
  • evidence_spans — record_type + record_id + field, paragraph_id, exact_quote (substring-proven).

Canonicalize (mentions → ideas, cards → frameworks)

Deterministic first pass (cluster.py): same normalized company + same stance + thesis token-overlap; manual merge/split via CLI. Never merge by ticker alone (D12): bull and bear theses on one company are different ideas, and opposite stances never auto-merge. Corroboration raises salience, never merit. Phase-2 gate: 100-file eligible-set audit — span-validity 100% on landed records; zero-idea rate on a political holdout reported.

12Phase 3 — Ranker PLANNED

Blueprint design only (§6 Scores, §7.4, §9 Phase 3). A deterministic function of features + a versioned ranker JSON — no LLM in the scoring path. Changing weights produces a new ranker_version and a new score_snapshots set, and never re-extracts (D14). The ranking objective is the expected value of Joseph's next research hour (D7); the system never predicts investment performance.

Decay & the D21 status overrides

  • v1 per-topic half-lives (hand-set, Joseph-tunable, live in the ranker JSON): geopolitics 21d · china-econ 45d · ai-tech 45d · finance-econ 90d · investment 90d · other 30d. Ideas with an extracted horizon use the horizon, not the topic default.
  • Decay governs the unlabeled majority only. Joseph's labels override it (D21): an accepted idea leaves the research queue for the outcome track (default 90-day due date when no horizon was extracted); a rejected idea's score floors at zero; helpful boosts a lesson's framework, not-so-much suppresses re-surface. The magnitudes are ranker-JSON tunables — Joseph never types numbers.
  • Expired ideas (expires_on < today) leave the research queue and appear on the outcome due-list.

Authors (D9) & the Phase-3 gate

  • Author quality = three variables: personal utility (learnable now), analytical traits (from extraction features), track record (empty until outcome data exists — no hallucinated prior). Author weight in idea ranking is capped at 0.15 of the weighted sum in v1.
  • The feedback_events SQLite mirror lands here (Phase-1 plan deviation 2) — the ranker is its first consumer.
  • rankers / score_snapshots tables make any past queue replayable: "why was this ranked #3 last Tuesday?" is answerable.
  • Gate: on the labeled set, the hand-tuned research queue must be not worse than all three baselines (recency-only, author-only, BM25-title) on nDCG@10; ties go to the simpler baseline.

Blueprint design only (§7.5/§7.6, §9 Phases 4–5). The review app grows from one calibration kind into the standing triage surface, and the remaining eligible backlog gets extracted.

Phase-4 gate

  • Extract the remaining eligible backlog (the "500-file extract").
  • Span-validity ≥95% on a 50-file re-audit.
  • Top-10 research queue is neither majority-one-author nor majority-politics.
  • Joseph completes one real weekly triage in the app.
  • Event-log hardening, promote, outcome due-list.

Phase 5 — steady state (the tail)

  • Incremental intake/gate/extract on new feeder files (~tens/week inflow).
  • kdb-fts export — versioned JSONL/CSV snapshots under exports/<date>/; the only coupling to the future GraphDB-comparison harness (which reads exports, not the package).
  • Calibration proposal command after ~200 events: a regularized pointwise model over the feature vector proposes a new ranker version — Joseph accepts or rejects; never auto-swapped. Validation is time-based (train on older ratings, validate on newer), never random shuffle. Learning-to-rank (LambdaMART etc.) stays out of v1.

The mechanical boundaries (both guard tests in tools/tests/test_package_boundaries.py)

  • Import contract (D2): ALLOWED["kdb_fts"] = {"common"} — kdb_fts imports nothing internal but common (call_model + retry + telemetry + model_pool + atomic_io), and nothing internal imports kdb_fts in v1 (the comparison harness, when built, reads exports).
  • Write-boundary guard (D3): sqlite3.connect, mkdir, and Path mutators are allowed only in ledger.py; every other file write in kdb_fts goes through common.atomic_io. kdb_fts never writes the wiki, manifest, graph, pipeline configs, feeder state, or the raw sources — the rule drifts silently if left to convention, so it's a test.
  • Test isolation: an autouse fixture in the root conftest.py redirects KDB_FTS_PATH to a per-test tmp dir — tests never touch the production ledger.

16Glossary

TermMeaning
gateThe cheap LLM pass (one call per ok article) that assigns a topic, a signal score, and extraction eligibility — deciding what deserves deep extraction (§6; D5).
verdictOne gate result: topic · signal · extract_ideas · extract_lessons · confidence · rationale, stored as a gate_verdicts row keyed by (article_id, run_id). Latest verdict routes; history kept.
freezerreview.py::freeze_batch — draws a deterministic stratified sample and writes it immutably to review/<batch_id>.json. "Frozen" = the sample, order, scores, and positions can never drift between sessions (§7).
batchA named, frozen set of articles for review (e.g. calibration-p1, 150 items). The frozen JSON doubles as the exposure record for every event written against it.
exploration sampleThe 5% (min 10) of gate-ineligible articles marked exploration=1 and extracted anyway in Phase 2 — measures the gate's false-negative rate (§6; §7.2). Distinct from the Phase-4 20%-of-batch-slots exploration quota (D13, deviation 9).
calibrationComparing gate verdicts against Joseph's labels on a frozen batch: kdb-fts calibration prints the confusion matrix + precision/recall/F1; Joseph sets the accept threshold (§10).
cleanlinessIntake's per-file classification: ok · short · media · digest-stub · bleed (precedence in that reverse order). Only ok articles are gated; the rest are skip-by-rule (§5; D16).
canonical authorThe deduplicated author entity in the authors table; author_aliases + Joseph's author_map.yaml map the 117 raw strings onto canonical names (§5; D9).
ledgerledger.sqlite — the SQLite system of record under <vault>/KDB/fts/; ledger.py is the only module allowed to open it (§5, §14).
exposure recordThe ranker version, score shown, and position shown at the moment Joseph judged an item — carried by the frozen batch JSON and stamped server-side onto every feedback event (§7–§9; D13).
skip-by-ruleClasses excluded from all LLM spend by deterministic rule, never by model judgment: media, short, digest-stub, bleed (D16).
ranker versionA named, versioned JSON object of weights + feature list + half-lives + status-label overrides; changing it re-scores without re-extracting (§12; D14/D21).
